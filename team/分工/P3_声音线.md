## 任务清单

### 1. TTS 多 provider

现在 `tts.py` 只有一个 `OpenAICompatibleTTSProvider`（L24）。要扩成多家。

参考：`MoneyPrinterTurbo/app/services/voice.py` 里有 10 家现成的可抄——
`edge / azure / siliconflow / minimax / gemini / mimo / chatterbox / kokoro / fish_audio / elevenlabs`

> ⚠️ 注意一个坑：**`siliconflow` 是云上跑 CosyVoice2**，看着像本地其实是云。要真正的本地推理得自己起服务，但接口形状可以直接沿用。

### 2. 词级/句级时间戳（你的核心交付物）

> **整段音频不算交付，带时间戳才算。**

产出 `cues: [{shot_id, start, end, text}]`。

**为什么这是核心**：这是音画同步的唯一基础。现在 `media.py:290-305` 的 `create_srt()` 是按镜头**名义时长均分**切字幕的——配音稍微长一点短一点，字幕就会渐进错位。有了真实时间戳，P4 才能把字幕和画面钉死。

获取途径：
- `edge_tts` 的 `SubMaker` 直接给词级时间戳（`voice.py:24` 有用法）
- 大多数云 TTS 也返回时间戳；没有的话用**强制对齐**兜底（可以让 DeepSeek 帮你对，或按标点切分后估算）

`contract.AudioResult.validate()` 会自动检查 cues 单调递增、不重叠、区间合法。

### 3. 音乐

现在只有 `media.py:242-249` 的 `find_music_file()`——从目录里**捞第一个文件**，和情绪毫无关系。

要按 `ALLOWED_MUSIC_MOODS`（舒缓 / 热烈 / 雅致 / 轻快）生成或匹配。

- 生成：`MoneyPrinterTurbo/app/services/elevenlabs_music.py` 有适配（但云+付费）
- 匹配：整理一批授权曲库，按情绪打标签，这是最省事也最稳的路
- 参考：`media.py:31-36` 里 `MOOD_FREQUENCIES` 已经定了四种情绪

### 4. ducking + 响度标准化

现在是 `renderer.py:118-123` 的 `amix` 固定音量——旁白和 BGM 一起响，听不清人声。

要做成**旁白说话时 BGM 自动压低**。

> ⚠️ 注意：`amix` 那段在 `renderer.py` 里，是 **P4 的文件**。你可以给出混音后的音频产物，但改 filter 链由 P4 做。**接口对齐后再动手**——这是你和 P4 唯一需要沟通的点。

---

## 你的输入 / 输出

**输入**：`narration` 文本 + `voice`（女声/男声）+ `rate`（语速）+ `music_mood`
**输出**：`contract.AudioResult`

契约里 `Cue` 的四个字段是硬性的。P4 的字幕和音画同步直接吃这个结构。

## 独立验证

```bash
cd zhejiang-tourism-aigc

python -m backend.app.providers.tts --text "西湖十景，四时不同" --out /tmp/v.wav --dump-cues
```

听一遍，核对 cues 时间戳和音频波形是否对得上。

没有 API 时用 `backend/app/providers/stubs/stub_audio.py` 顶上：

```bash
python backend/app/providers/stubs/stub_audio.py --out-dir /tmp/fake --shot-count 6 --dump-cues
```

**验收标准**：cues 里每一句的 start/end 和实际音频里那句话的位置能对上，误差在人在听觉上察觉不到的范围。

## 交付方式

本项目**不使用远程仓库**。各自完工后，把成果打包发回给负责人合并。

**只发你名下的文件 + 你的 AI 日志**，打包成一个文件夹：

```
P3-交付-<日期>/
├── backend/app/providers/tts.py
├── backend/app/providers/music.py

├── P3-AI-LOG.md
└── 说明.md
```

### 两条硬要求

1. **只发自己名下的文件。** 如果你改了别人的文件，说明越界了——发回来会被退回。
   （没有版本控制，负责人只能靠文件清单判断你有没有越界。）
2. **必须发 AI 日志。** 日志是负责人唯一能知道「你改了什么、为什么这么改、
   AI 哪里写错了、你有没有真的验证过」的来源。没日志的交付不予合并。

### 说明.md 里写三件事

- **新增的环境变量**（负责人要同步进 `.env` 和 `.env.example`）
- **新增的依赖**（负责人要同步进 `requirements.txt`）
- **你验证时跑了什么命令、结果如何**

### 负责人那边的合并方式

你不需要会 git。负责人本地有仓库，会：

```bash
git diff --stat          # 先看你改了哪些文件
git diff <文件>          # 再具体看改了什么
git add -A && git commit # 确认没问题才提交
```

所以**别改别人的文件**——一改就会在 diff 里显形。

# 合并计划（负责人用）

> 核心思想：**链路从第一天起就是通的，只是内容是假的。**
> 之后每合入一条真产线，成片就升级一格，全程不出现「等谁做完才能跑」。

---

## 合并顺序

| 轮次 | 合谁 | 为什么排这个位置 | 验收标准 |
|---|---|---|---|
| 0 | **契约 + stub** | 骨架。先让假数据出片 | 30 秒 MP4，11/11 测试通过 |
| 1 | **P1 编排** | 主干，不落地后面插不进来 | Registry 生效，链路仍通，**阶段顺序已改为 audio→assets** |
| 2 | **P4 渲染** | 零外部依赖、零成本、最好验证 | 有运镜/调色/转场，**仍严格 30.000s、720×1280、25fps** |
| 3 | **P3 声音** | 依赖 P4 的 mux 和字幕接口 | 真配音 + 真音乐 + ducking + 字幕对得上真实 cues |
| 4 | **P2 画面** | 最贵最慢、有外部风险，放最后但风险最高 | AI 画面进链路，6 镜头风格统一 |

**P4 先合的理由**：它零外部依赖、零成本、最容易验证。先合它，后面 P2/P3 接进来时渲染侧已经是稳的。

---

## 每轮合并前的三道检查

```bash
cd zhejiang-tourism-aigc    # 项目根

# 1. 有没有人动了契约（必须全空）
grep -h "契约影响" team/AI日志/P*-AI-LOG.md | grep -v "无"

# 2. 有没有「未验证」的条目悬着
grep -n "未验证" team/AI日志/P*-AI-LOG.md

# 3. 各条产线的进度
grep -c "^## Entry" team/AI日志/P*-AI-LOG.md
```

**第 1 条只要不是空的，立刻停下全员同步。** 契约是四个人唯一的耦合点，私自改字段会让合并时的报错极难定位。

第 2 条不阻塞合并，但**要在合并日志里写明哪些是未验证的**——不能把「AI 说能跑」当成「验过了」。

## 每轮合并后的固定回归

```bash
cd zhejiang-tourism-aigc

python -m compileall -q backend tests
node --check frontend/app.js
python -m unittest discover -s tests -v      # 底线：11/11

# 端到端
DEFAULT_PROVIDER=offline ALLOW_SYNTHETIC_AUDIO_FALLBACK=true \
  powershell -File scripts/smoke-test.ps1

# 成片规格（每一项都不能退化）
ffprobe -v error -show_entries format=duration -of csv=p=0 runtime/media/<task_id>/final.mp4
ffprobe -v error -select_streams v:0 -show_entries stream=width,height,r_frame_rate -of csv=p=0 runtime/media/<task_id>/final.mp4
ffprobe -v error -show_entries stream=codec_type -of csv=p=0 runtime/media/<task_id>/final.mp4
```

### 三条不能破的指标

| 指标 | 值 | 谁最容易破坏它 |
|---|---|---|
| 总时长 | **30.000 秒** | P4 —— xfade 转场会让总长变短 |
| 分辨率 | 720×1280 | P4 —— 运镜的 scale 参数 |
| 帧率 | 25 fps | P4 —— zoompan 的 fps 参数 |

> 这三条是现有版本已声明并验证过的确定性指标。P4 的改动最容易打破它们，**每次合 P4 都要重点验这三条**。

## 合并时的冲突处理

**文件所有权是硬边界**，正常不该有冲突。真撞上了，说明有人越界了：

| 冲突文件 | 双方 | 处理 |
|---|---|---|
| `orchestrator.py` | P1 vs 任何人 | 别人越界。以 P1 为准，越界方改回自己文件 |
| `renderer.py` | P4 vs P3 | P3 想改混音 filter 链。按契约：**P3 出音频产物，filter 由 P4 落地** |
| `providers/media.py` | P3 vs P4 | **契约交付时就该拆掉**（见下） |
| `contract.py` | 任何人 | 无冲突空间——只有负责人能改 |

### ⚠️ 契约交付时必须先拆 `providers/media.py`

它同时装着 P3 要的 `find_music_file()`（L242）和 P4 要的 `run_ffmpeg()` / `create_srt()`（L160 / L290）。不拆的话 P3 和 P4 会天天改同一个文件。

- TTS / 音乐相关 → 挪进 `providers/tts.py`（归 P3）
- FFmpeg / 字幕相关 → 挪进 `providers/media_ffmpeg.py`（归 P4）

这是纯搬运，但**必须在分工开始前做完**。

## 降级链（最后接）

所有云 provider 都接完之后，接降级链：

```
cloud-i2v → cloud-t2i → local-library → offline
                                        ↑
                              OfflineAssetProvider
                              （media.py:30-86，丑但永远能跑）
```

断网 / 限流 / 欠费时自动往下走一格，往 trace 记 `fallback_used=true` 和原因。

**`OfflineAssetProvider` 必须保留。** 它是演示永不翻车的保险——答辩现场网络出问题，还能出一个虽然丑但完整的片子，比黑屏强。

---

## 最终验收

全部合并完后，用**真实链路**跑一遍（`DEFAULT_PROVIDER=deepseek`），确认：

```text
trace.provider        = openai-compatible
trace.model           = deepseek-chat
trace.fallback_used   = false
render.has_audio      = true
render.has_burned_subtitles = true
```

外加三项这次新增的能力要能演示：

| 能力 | 怎么验 |
|---|---|
| 画面在动 | 播放成片，静图有推拉运镜；AI 生成镜头本身有运动 |
| 风格一致 | 6 个镜头并排看，色调统一 |
| 音画同步 | 字幕出现时机和配音重合，不渐进错位 |

## 风险提示

| 风险 | 什么时候会爆 | 应对 |
|---|---|---|
| API 配额/欠费 | P2 合并那轮 | 降级链兜底，演示不受影响 |
| 转场打破 30.000s | 每次合 P4 | 每轮都验 duration |
| 契约被私改 | 合并时突然报字段错 | grep 日志第 1 条 |
| 云生成太慢拖长演示 | 现场 | 提前预渲染主案例作备份 |
| 阶段顺序没统一 | P1 合并后全链路错位 | 合并 P1 那轮重点验 audio 是否先于 assets 跑 |
